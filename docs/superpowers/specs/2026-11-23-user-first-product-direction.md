# Summrise：以用户可用性为主线的产品方向与路线图

日期：2026-11-23（UTC）。这是产品规划和设计决策，不是已实现功能、市场调研或上线承诺。当前重构与发布继续按原验收流程推进。

## 1. 产品定位

**让 AI 使用用户自己的机器，同时让用户掌握机器身份、授权和可核验的工作结果。**

普通用户的理想路径是：安装 → 登录并绑定机器 → 连接已有 AI 客户端 → 完成第一件事 → 看懂结果、恢复失败、收回后续访问。域名、证书、端口、签名格式和事务字段应由产品处理。

首要用户假设：已经在使用 AI，希望它能检查项目、读取文件、运行测试或完成本机工作的个人和小团队。先验证这类用户的完整路径，再扩大到其他人群；目前没有可声称的留存、转化率或付费意愿数据。

产品主线选择：**官方托管为默认，本地使用完整可用，自托管为高级选择；信任和数据可迁移。** 不要求普通用户先拥有域名、服务器、Cloudflare 账号或钱包。

## 2. 使用方式与托管方案

| 方式 | 用户需要做什么 | 服务承担什么 | 适用场景 |
|---|---|---|---|
| 官方托管，默认路径 | 安装、登录、配对自己的机器、授权 AI | 稳定 HTTPS/MCP 地址、账号、连接、隔离、升级与恢复入口 | 个人和小团队的远程 AI 使用 |
| 本地使用 | 安装，在同机 AI 客户端连接 | 本机执行与记录；本地地址无需公网域名 | 本机开发、离线或隐私要求高的工作 |
| 自托管 | 管理自己的 Console、网络与数据 | 同一套产品与协议，提供清晰部署和迁移指引 | 技术用户、组织内网、合规环境 |

官方托管的是连接、控制和管理入口；执行仍发生在用户选定的机器上。机器休眠、断网或退出时，要明确显示不可达与最后读取时间。

托管服务会处理经它转发的调用和响应，产品必须清楚说明内容处理、保留期限与导出/删除行为。设备签名或链上检查点不等于端到端加密；本地连接也不代表用户选用的 AI 模型在本地运行。

当前 Device 已主动连接 Console，因此官方服务提供稳定入口后，用户设备无需开放公网入站端口，也无需每台机器再配置一个 Cloudflare 隧道。

**选定的技术方向：** 首期继续使用现有 Rust Console 与 Device，Cloudflare 可承担域名、HTTPS、防护和官方服务的隧道入口。官网静态 Worker 与有持久状态、长连接的 Console 分工明确。Workers + Durable Objects 是可评估的托管方案，采用它需要存储与连接适配；当前不为托管目标整体重写已有后端。

考虑过的替代方案：

- 只提供自托管：适合技术用户，首次使用的域名、运维与配置门槛较高，保留为高级路径。
- 完全迁移到 Cloudflare Workers：平台提供长连接能力，但现有原生 Console 需要适配；先验证现架构能满足用户目标。
- 每用户独立 Console 实例：可作为邀请内测的隔离实现，但必须先验证签名信任、密钥分配和运维成本；不能假定独立数据目录等于完整隔离。
- 公链作为日常控制平面：增加确认等待、钱包和网络依赖；第一阶段采用可本地核验的身份与授权，公开证明作为可选层。

## 3. 首次使用应呈现的内容

```text
登录 Summrise
  ↓
安装并配对“我的电脑”
  ↓
选择 AI 客户端，生成连接配置
  ↓
选择本次权限：查看信息 / 读取文件 / 执行程序
  ↓
完成一项示例任务，看到本次结果与记录
```

安装后的目标是至多三次关键人工操作：登录、配对、连接客户端。AI 侧应自动处理必要的工作上下文；用户不需要理解 txn、MCP 传输会话或工具 JSON。

连接方式按真实客户端验证：至少先做好一种桌面客户端和一种远端客户端。需要 OAuth 的客户端必须完成相应接入，不能以 curl 成功替代其兼容验收。

**只读工作要能独立开始。** 工作会话与操作系统终端应分开：读取文件不应为了创建事务上下文而先要求启动 Shell。当前文案修正只说明现有约束，后续需要独立的逻辑工作上下文设计与 Device 强制执行。

主界面沿用浅色 A3 和 Overview / Machines / Activity / Access 四个主入口。默认突出当前机器、当前任务、允许做什么、结果和下一步；工具 schema、密钥指纹、事务和连接诊断进入高级区。官网默认介绍能完成的工作与实际可用的上手路径，托管功能开放前明确标注状态。

## 4. 值得做的创新

| 创新 | 用户获得的价值 | 是否需要区块链 | 主要实现边界 |
|---|---|---|---|
| 机器通行证 | 机器有可验证身份，更换连接服务后仍能辨认它 | 不需要 | 利用设备公钥；补所有权、轮换、恢复和迁移协议 |
| 任务授权卡 | 清楚看到哪一个 AI、哪台机器、哪些能力、何时到期；可撤销后续访问 | 不需要 | Device 执行约束；授权委托只可缩小；终端权限单独说明 |
| 可恢复任务 | 断线后找到同一任务与结果，减少重复执行 | 不需要 | 稳定任务 ID、幂等与状态查询；未知结果不自动重跑 |
| 可验证任务收据 | 核对结果来自哪个设备密钥、内容是否被改动 | 不需要 | 带领域分隔的设备签名、明确状态、可导出验证器 |
| 可选择的连接服务 | 可用官方服务、自己的服务或未来的直连/中继 | 不需要 | 保留设备身份；迁移需本机所有者授权并撤销旧信任 |
| 独立公开检查点 | 在多人协作或审计中证明某批收据在公开检查点前已存在 | 可选 | 可用透明日志或链上批次根；日常工作不等待它 |

### 机器通行证

现有设备密钥是基础，不宣称当前已实现 DID 标准或账号恢复。后续可研究 DID 表达和跨服务解析；人类可见的是机器名称与身份确认。密钥丢失、设备转让和发行者更换需要明确恢复与撤销流程。

### 任务授权卡

卡片首先表达机器、工具、有效期和本次用途。目录限制只有在文件能力实际强制执行时才显示；普通终端执行不可包装成目录沙箱。撤销阻止后续请求，已接受或已运行任务需单独显示状态和可用的停止操作，不能承诺自动撤销已发生的写入。

### 可恢复任务与收据

网络超时必须区分“确定未发送”和“结果未知”。长命令使用可查询的任务身份，丢响应后查询同一任务；幂等键与执行状态要由设备确认，不能仅靠 UI 防重复点击。

收据包含设备/任务身份、授权关联、完成状态、退出事实、输出摘要及截断标记。先提供离线验签与导出。签名证明签发来源与记录完整性，不证明命令逻辑正确、结果有用或设备未被入侵。缺少设备完成答复时不能伪造一张设备签名的成功收据。

### 区块链的具体位置

钱包登录可以成为可选身份入口，常规登录和恢复保持可用。钱包签名登录本身可以是链下行为，需校验域名、nonce、有效期与重放；不要求每条命令发链上交易。

如果团队确有独立见证需求，再评估批次 Merkle 根或公开检查点。文件、命令、输出、令牌和个人标识不进入公链；连低熵内容摘要也需考虑关联与猜测风险。链不可用时，本地执行、撤销判断和查询仍按已定义规则工作。

去中心化身份不必依赖区块链。公链也不会单独解决稳定公网入口、离线机器、权限撤销或连接中继问题。

## 5. 官方托管必须先补的基础

当前 Console 面向一个管理员空间：认证、设备、令牌、连接和记录共享全局上下文。多人使用需要真正的服务端隔离。

1. 认证产生稳定用户身份，贯穿请求；邮箱通过验证不能直接变成全局管理员。
2. 以工作空间隔离设备所有权、配对码、令牌、授权和持久数据；个人空间初期只有一个成员。
3. HTTP、MCP、舰队目录、设备连接、截图、运行结果及审计流都检查相同归属，前端过滤不承担隔离。
4. 配对码把设备绑定到发行该码的空间；重放、过期、转移和移除有明确结果。
5. 签名钥匙与 Device 信任契约先验证；不向每个隔离实例分发不受约束的全局签名能力，不增加 accept-any 信任模式。
6. 公共注册前完成两个空间的端到端越权测试、恢复演练、配额与数据导出/删除行为。

内部采用租户上下文还是隔离进程，由隔离与信任试验选定；这是工程决策，不改变用户的免部署路径。

## 6. 里程碑顺序

| 阶段 | 交付给用户的结果 | 完成标准 |
|---|---|---|
| M0 当前重构发布 | 浅色界面、真实状态、完整失败结果、能照做的文档和可下载版本 | 精确 main 提交、完整 CI、签名产物、实际部署、线上版本与资源一致；未验平台明确状态 |
| M1 免部署个人版内测 | 官方账号/空间、设备配对、稳定 MCP 地址、最小权限首次任务 | 两空间零越权；无域名/服务器/钱包仍能使用；只读起步不需要 Shell；至少两类客户端实测 |
| M2 可靠工作与差异化 | 任务身份、断线恢复、授权卡、离线可验证收据 | 丢响应不重复执行；失败输出可见；到期/撤销后续调用拒绝；篡改收据验签失败 |
| M3 小团队 | 空间成员、设备共享、角色与责任记录 | 邀请/移除/角色变更全链生效；个人与团队数据边界可验证 |
| M4 可迁移与规模化 | 自托管迁移、可选直连/中继、按真实需求增加外部见证 | 迁移不默换机器身份，旧信任撤销；直连失败有可用回退；容量/成本和恢复达到实测目标 |

按里程碑验收排期，当前没有能支持固定发布日期的容量和用户研究。M1 先受控邀请，建议个人内测上限三台机器，再根据负载和使用情况调整。该配额是规划选择，尚未实现。

M0 的当前修复与发布不等待整套托管或区块链项目。已经发现的记录连续性、UTF-8 历史与服务共享所有权等问题列入可靠性工作包，在对应暴露路径开放给新用户前验证。

## 7. 验证用户价值

首轮采用人工首次使用演练和明确同意的反馈，不增加默认收集命令或文件内容的遥测。

- 北极星：每周至少完成一次“有可核验结果的真实工作”的用户数；不以调用次数或工具数量替代价值。
- 首次使用目标：十名不了解部署的新用户中，至少八名不靠工程师帮助，在十分钟内完成首个真实任务。
- 核心一致性：用户始终能辨认当前机器、权限和结果；不把未知显示为成功、零条或已停止。
- 恢复：断网、设备休眠、权限到期、客户端重连时给出下一步，保留原任务身份。
- 所有上述比例、时长和配额均为拟验收目标，当前基线未知。

## 8. 成本与范围

先投入安装/配对、官方托管、最小权限和失败恢复。服务成本重点验证长连接、截图/终端流量、记录保留与支持成本；命令计算主要发生在用户机器上。早期不承诺无限免费资源。

后续商业化优先围绕团队协作、管理、可靠性和服务额度验证需求。币、NFT、按命令上链以及向陌生人出租算力不进入首期；算力市场涉及独立的隔离、计量、支付和仲裁产品。

## 9. 依据与技术边界

源码基线来自当前候选审查，而非宣称官方托管已完成：

- [Console HTTP](../../../device/console/src/http.rs)：全局管理员上下文与代理边界；[认证](../../../device/console/src/auth.rs)、[设备](../../../device/console/src/devices.rs)、[配对码](../../../device/console/src/codes.rs)、[令牌](../../../device/console/src/tokens.rs)目前需要账号归属设计。
- [Device 连接](../../../device/device/src/console.rs)：主动连接、重连与信任；[mesh](../../../device/mesh/src/lib.rs)已有连接协调/QUIC/中继基础，Console operator 流接入仍需开发验收。
- [Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/)采用出站连接；[Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)是临时测试入口、地址会变化且不支持 SSE，不作为稳定产品接入。
- [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)与[Durable Objects WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)说明可选平台能力；[代理连接限制](https://developers.cloudflare.com/fundamentals/reference/connection-limits/)需要长任务设计主动适配。
- [W3C DID Core](https://www.w3.org/TR/did-core/)支持多种登记与解析基础；[Verifiable Credentials 2.0](https://www.w3.org/TR/vc-data-model-2.0/)明确“可验证”不等于声明内容本身为真。当前规划不声称标准实现已完成。
